\begin{abstract}
Standard UUID generators cannot embed application-defined structure (a shard, a tenant, or a monotonic counter) inside a standards-compliant identifier without paying rejection sampling's exponential cost. RFC 9562 makes this gap explicit. Version 8 reserves 122 bits for exactly this purpose but defines no algorithm to fill them. We close this gap with GenoID, a declarative composition framework that produces valid v8 UUIDs from fields constrained over allowed-set, range, and monotonic vocabularies at $O(k)$ repair cost, against an expected $64^k$ draws per identifier under joint whole-UUID rejection, whose geometric tail has no upper bound on any single run (the 8-bit, 4-value special case), with a proven total-variation bound $m/2^\ell$ on every allowed-set repaired field, measured throughput $2.8$--$12.9\times$ over the closest prior art (\texttt{pg\_uuid\_v8}, and $2.2$--$14.5\times$ over \texttt{ulid-v8}) across nine CI environments, and byte-identity across an independent Rust reimplementation. It remains slower than \texttt{crypto.randomUUID()} and Snowflake (different guarantee classes); the ratio claim is against the closest structured prior art only. The design is backed by formal complexity and entropy accounting, a NIST SP~800-22 battery reported as a sanity check on the pooling path rather than security evidence, and an explicit adversarial security analysis that separates GenoID's architectural contribution from the CSPRNG-inherited randomness quality beneath it. By making shard, tenant, and sequence identity a declarative property of the key itself, GenoID targets the data-systems layer directly.
\keywords{distributed data systems, sharding, UUID, RFC 9562, constraints, evaluation}
\end{abstract}

\section{Introduction}

Imagine ten database servers where each record's ID must reveal which one owns it. RFC~9562's v8 UUID reserves 122 bits for application-defined structure but specifies no algorithm to fill them. GenoID is that missing algorithm: instead of rejection sampling's expected $64^k$ draws, it produces correct keys on the first try in $O(k)$ work.

Existing UUIDs fall short: v4 carries no structure, v7 fixes one timestamp layout, and \texttt{pg\_uuid\_v8} embeds an encrypted timestamp with no multi-field composition. Structure in the key is not always the right choice; a composite key is simpler whenever the identifier never leaves the database, as discussed in Section~\ref{sec:why-embed} states the conditions under which it is, and Section~\ref{sec:composite-bench} quantifies the cost of the alternative. GenoID declares field structure once as a \texttt{V8Layout} and satisfies it by deterministic repair, drawing from pre-populated CSPRNG pools to amortize entropy cost.

\noindent\textbf{Contributions.}
\begin{itemize}
    \item A declarative RFC~9562 v8 layout abstraction for typed, constrained fields.
    \item A pooled generation architecture that amortizes CSPRNG draws, entropy-neutral by construction.
    \item Constraint-guided repair: $O(k)$ per UUID vs an expected $64^k$ draws under rejection sampling.
    \item A proven total-variation bound $m/2^\ell$ on every allowed-set repaired field, with exact-fibre conditions on both shipped repair paths.
    \item An adversarial security analysis disclosing the bounded forward-secrecy window and by-design metadata leakage of structured layouts.
    \item Validation across per-field uniformity at $10^8$ scale (matching the closed-form $m/2^\ell$ bound to within $0.012$ percentage points, consistent with the $0.004$ pp binomial sampling noise at $n=10^8$), NIST and dieharder batteries, and multi-runtime throughput benchmarks, with limitations disclosed openly.
\end{itemize}

\section{Design}
\label{sec:design}
Think of a UUID's 122 free bits as a form with labeled blanks: timestamp, shard from a small set, monotonic counter. GenoID lets a developer declare that form once and fills every blank correctly on every call.

\medskip
\noindent\emph{Example:} a \texttt{dbkey} UUID for shard~3 at time~$t$: the first 48 bits read as $t$, the shard byte reads 3, a router extracts ``shard~3'' directly from the key. Remaining bits are random.

\subsection{Declarative layout}
\label{sec:layout}
A \texttt{V8Layout} declares ordered \texttt{V8Field}s with bit offset, length, type, and optional constraint.

\begin{lstlisting}[caption={The \texttt{dbkey} layout declaration. Bit ranges 48--51
           (\texttt{ver}) and 64--65 (\texttt{var}) are never declared:
           \texttt{completeLayout} reserves them per RFC~9562 and fills
           every remaining undeclared range with random filler.},
  label={lst:dbkey}]
const dbkey: V8Layout = {
  name: "dbkey",
  fields: [
    { name: "timestamp", offset:  0, length: 48,
      type: "timestamp-ms" },
    { name: "shard",     offset: 52, length:  8,
      type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4,5] } },
    { name: "counter",   offset: 66, length: 16,
      type: "counter",
      constraint: { kind: "monotonic" } },
  ],
};
\end{lstlisting}

Listing~\ref{lst:dbkey} is the complete specification: no generation code is written per layout, and the same \texttt{repairConstraints} pass (Algorithm~\ref{alg:repair}) serves every declaration. Substituting \texttt{allowed: [1..5]} with a 12-bit tenant enum and an 8-bit region enum yields the \texttt{multitenant} layout without touching the generator. (Offset~52 is the shipped \texttt{shard} baseline; byte-alignment remains validator-enforceable style guidance with no measured performance implication, per Section~\ref{sec:composite-bench}.)

\subsection{Implementation: pooled CSPRNG generation}
\label{sec:pooled-gen}
A 256-entry pool is populated from the OS CSPRNG on first use and
refilled in full when exhausted. Each call draws one 128-bit value from
the pool; the single shared \texttt{repairConstraints} pass
(Algorithm~\ref{alg:repair}) then fixes any constrained field that falls
outside its admissible set.

\subsection{Constraint-guided repair}
\label{sec:repair}

\begin{algorithm}[!ht]
\caption{\texttt{repairConstraints}: single-pass constraint satisfaction}
\label{alg:repair}
\begin{algorithmic}[1]
\Require Layout $L$ with fields $f_1..f_n$; candidate 128-bit value $u$
\Ensure  $u'$ satisfying every \textsc{allowed}-set and \textsc{range} constraint declared in $L$ (shipped layouts declare at most one per field; monotonic fields: Lemma~\ref{lem:counter})
\Statex
\For{each $f \in L.\textit{fields}$ with $f.\textit{constraint} \in \{\textsc{allowed},\, \textsc{range}\}$}
  \State $v \gets \textsc{ExtractBits}(u,\, f.\textit{offset},\, f.\textit{length})$
  \State $c \gets f.\textit{constraint}$
  \If{$c.\textit{kind} = \textsc{allowed}$}
    \State $v' \gets
           \begin{cases}
             v & v \in c.\textit{allowed} \\
             c.\textit{allowed}[\,v \bmod |c.\textit{allowed}|\,] & \text{otherwise}
           \end{cases}$
            \Comment{$O(1)$}
  \ElsIf{$c.\textit{kind} = \textsc{range}$}
    \State $v' \gets \max\bigl(c.\textit{min},\ \min(v,\, c.\textit{max})\bigr)$
            \Comment{$O(1)$}
  \EndIf
  \State $u \gets \textsc{WriteBits}(u,\, f.\textit{offset},\,
          f.\textit{length},\, v')$
\EndFor
\State \Return \textsc{SetVersionVariant}(u)
        \Comment{RFC~9562 \S4.2}
\end{algorithmic}
\end{algorithm}

Every branch assigns $v'$ unconditionally, so the loop body cannot fail and the procedure contains no backward jump: it executes exactly $k$ iterations for $k$ \textsc{allowed}- or \textsc{range}-constrained fields, independent of the drawn value. Correctness is by construction: each branch's codomain is the constraint's satisfying set: 0 violations, not ``near 0.'' \textbf{Lemma (tick-keyed counter).}\label{lem:counter} Monotonic fields never enter the loop: they are resolved by the pool refill path's tick-keyed counter logic before \texttt{repairConstraints} is called, which clamps the timestamp to $\max(\textit{clock}, \textit{last tick})$, increments the counter within a tick, and freezes generation until the clock advances on exhaustion, so no emitted pair moves backwards. Both generator paths implement this (pooled refill loop and compiled prologue).

Figure~\ref{fig:pipeline} shows a single repair: a drawn candidate whose \texttt{shard} field reads 7 is mapped to the admissible value 3.

With $\ell_c=16$ and $g=1$, reseeding leaves at least $2^{15}=32768$ increments per millisecond. At 3040~UUIDs/ms the counter advances once per UUID, yielding a $\sim10\times$ margin before the rollover path. Per-generator state is isolated; concurrent generators require no locks.

\section{Applications}
\label{sec:applications}
Each use case below declares one layout and reads one field; no
generation code is written per application.

\subsection{Why embed structure in the key?}
\label{sec:why-embed}

The obvious alternative to embedding a shard in the identifier is to keep
it beside the identifier: a composite key
$(\textit{shard\_id}, \textit{uuid})$, or a separate indexed column. That
design is simpler than anything in this paper, and it is better on three
axes we do not contest. Resharding becomes a column update rather than a
layout migration and a dual-read window. The identifier retains all 122
random bits, so none of the entropy accounting in
Section~\ref{sec:entropy-accounting} applies. And the shard count is not
bounded by a field width fixed at declaration time.

Embedding wins in one specific circumstance: when the identifier must
cross a boundary that carries a single value. A URL path segment, a cache
key, a queue partition key, a log line, or a foreign key in a system one
does not control each admit one identifier, not two. A composite key
crossing such a boundary degrades to string concatenation, an ad-hoc,
unvalidated encoding of precisely what \texttt{V8Layout} specifies
formally, and the concatenated form is no longer a UUID, forfeiting
the native 16-byte column type, its index representation, and the library
and tooling support that RFC~9562 conformance carries.

A second, narrower benefit is integrity. When the tenant is a projection
of the key rather than a neighbouring column, a row whose key-embedded tenant
disagrees with its session context is detectable without a join rather than
requiring one: two columns can drift, one cannot. Still enforce authorization
and row-level security on the session value; never trust the key-embedded tenant,
which any key holder can forge or enumerate.

We therefore position GenoID for stable shard and tenant sets whose
identifiers escape the database, and not for elastic partitioning behind
a boundary the application fully controls.

Do not embed when the identifier never leaves the database (a composite
key is simpler and keeps all 122 random bits), when the shard set churns
(each resharding is a layout migration with a dual-read window), or when
tenant concealment matters: structured bits leak by design
(Section~\ref{sec:security}), and XOR-masking after repair (as in
\texttt{pg\_uuid\_v8}) composes mechanically but destroys exactly what
embedding buys, prefix prunability and range locality, so choose
masking for concealment or plaintext for routing, not both.

A resharding migration has a fixed shape. Version layout names as
\texttt{owner dbkey.v2}, never reuse a bare name across generations, and run the
dual-read window with readers accepting both generations (the versioned-layout
\texttt{readStructured} reader over \texttt{dbkey.v1} plus \texttt{dbkey.v2}) while writers emit the
new one; track the fraction of old-generation keys as the migration metric and
retire the old reader when it reaches zero. Size monotonic counters from peak
burst: a counter field admits $2^{\ell_c}$ increments per millisecond tick, and
generation blocks until the clock advances past any exhausted tick, so a burst
above budget stalls rather than degrades. Clock backsteps are safe by
construction (the tick clamps to $\max(\textit{clock}, \textit{last tick})$, so a
backstep re-emits the previous tick and a VM pause stalls); monitor stall
duration at the application level, since the generator exposes no stall counters
of its own (a blocked-count/stall-duration hook is future work). Where tenant or shard values must not be enumerable, keep them out
of URLs, logs, and caches: structured bits are readable by anyone holding the
key, and enumeration of a small set such as \texttt{tenant} $[1,8]$ is trivial.

\subsection{Cost of embedding versus a composite key}
\label{sec:composite-bench}

Section~\ref{sec:why-embed} claims a composite key does not help a lookup
arriving without its shard. We test this against five alternatives over
one workload, all arms using the same timestamp-sorted 128-bit identifier
under \texttt{WITHOUT ROWID} clustered storage, so the only variable is
where the shard resides.

Given a primary key $(\textit{shard},\textit{id})$, a lookup by
identifier alone cannot seek the index: \texttt{EXPLAIN QUERY PLAN}
reports \texttt{SCAN}, and latency grows linearly in table size against
the embedded key's logarithmic growth. Answering such a query therefore
requires a secondary index on \textit{id}, and that is the comparison
that matters, since any deployment facing this access pattern would add
one.

The secondary index is what embedding avoids. It carries $1.99\times$ the
storage per row ($56.4$ against $28.4$ bytes) and sustains $1.88\times$
lower insert throughput, while still resolving lookups $1.29\times$
slower, since resolution descends the secondary index and then the primary
key, where the embedded form descends once. Embedding serves both access
paths with a single index. Its advantage is the \emph{combination}: the
embedded arm is the only arm that is simultaneously near-best on insert,
near-best on bare-identifier lookup, and free of the second index.

Two comparisons show no difference and we report them as such: insert
throughput is within 15\% between the embedded key and an
unindexed composite key ($291$K vs $250$K rows/s), and point-lookup latency is indistinguishable between the
embedded key and a concatenated text key ($11.7$ vs $12.8\,\mu$s, CIs
overlap). Concatenation nonetheless costs $1.85\times$ the storage and
$1.24\times$ lower insert throughput, and is no longer a UUID, forfeiting
the native 16-byte column type and RFC~9562 tooling.

The conceded alternative, a plain key plus an expression index
extracting the shard, is measured in the same table. It costs
$1.93\times$ the storage ($54.9$ against $28.4$ bytes/row) and
$2.07\times$ lower insert throughput ($141$K vs $291$K rows/s) for lookup
parity with embedding ($12.2$ vs $11.7\,\mu$s, CIs overlap), while its
shard scan matches the embedded predicate scan ($30.6$ vs $22.7$\,ms)
rather than the composite's leading-column seek ($7.4$\,ms). The
expression index is the same price as the composite's secondary index
with none of its scan advantage: where the key must carry routing,
embedding still wins; where it need not, the expression index trades
insert throughput for tooling, not for savings.

We also withdraw a claim an earlier revision of this paper made, that
declaring the shard at a byte-aligned offset (56 rather than the shipped
52) yields a lookup advantage. Across four repeated runs of the same
experiment the direction of the effect reversed three times ($+14\%$,
$-2\%$, $+4.7\%$, $+4\%$ in favour of the aligned offset), i.e.\ it is
not separable from run-to-run variance at these trial counts, and SQLite
evidently evaluates the straddling two-byte predicate as cheaply as the
byte-aligned one. The aligned-offset variant was measured on the same rig
and is archived in \texttt{results/db-sqlite-composite.json}, but it is
not a table arm: alignment remains validator-enforceable style guidance
for engines with a different cost model, with no performance claim here.

We claim no advantage on shard-major scans, where the composite key's
leading column is the better structure: the composite and
composite-indexed arms resolve the shard range scan in $5.7$--$7.4$\,ms
against $22.7$\,ms for the embedded arm, a $3.1\times$ difference.
Embedding trades partition-scan speed for single-index storage and
bare-identifier seeks.

The same arms run against native engines. At $N=10^5$ rows per build over three
distributions (uniform, hot-tenant, bursty) on PostgreSQL~18.7 and MySQL~8.0.46
(local host, \texttt{bytea}/binary primary key,
64-byte payloads), the structured arm inserts at parity with UUIDv7 on PostgreSQL
($164.6$K versus $160.7$K rows/s, p50 over 5 reps) while the shard-first arm trails
($139.4$K rows/s); on MySQL both structured arms lead ($76.8$K and $74.6$K versus
$58.3$K rows/s, $+32\%$/$+28\%$ over v7). Point lookups and range scans show no
arm separation on either engine (100-probe lookup sets within $\approx 10\%$ on
PostgreSQL and $\approx 6\%$ on MySQL; range scans within $\approx 7\%$).
The tracked artifact
(\texttt{results/db-native.json}, with per-rep percentiles, query plans, and
server versions) records the $N=10^5$ result — with the same single-host caveat that
applies to every absolute rate in this section. The committed harness measures both engines, and
the CI \texttt{native-db} job re-runs the same scaled invocation against
PostgreSQL~18 and MySQL~8 service containers on every main push.

\subsection{Extension to clustered storage engines}
The preceding measurements use SQLite because it requires no external daemon, but the underlying B+\!tree locality argument is confirmed on production clustered-storage engines: PostgreSQL~18.7 shows the structured arm at parity with UUIDv7 on inserts ($+2\%$) with parity elsewhere, and MySQL~8.0 shows both structured arms ahead ($+32\%$/$+28\%$), each at $N=10^5$ rows per build with \texttt{bytea}/binary primary keys. The single-host caveat applies: neither the page layout, the WAL policy, nor the cost of a secondary index translates unchanged to other deployments. The benchmark harness for both native engines is committed alongside this paper (\texttt{src/scripts/bench-db-native.ts}, with seven identifier arms, three key distributions, percentiles over $\geq 5$ reps, query plans, storage, and WAL accounting, and a validator that refuses an incomplete result), and the CI \texttt{native-db} job re-runs it at the same scale against PostgreSQL~18 and MySQL~8 service containers, so the experiment can be re-run and audited without reimplementation.


\subsection{Sharded databases}
Listing~\ref{lst:dbkey} embeds the owning shard directly in the key.
A router extracts bits 52--59 and dispatches without consulting a
shard map as a mechanism: routing becomes a bit-mask and a comparison, replacing a
hash computation and a ring lookup under consistent hashing in the single-key case
(no cluster-scale routing experiment; cross-node dispatch and resharding cost remain future work). The 48-bit timestamp prefix orders keys by emission
time; on 16-byte binary storage this yields the insert and lookup
behaviour of Table~\ref{tab:composite}, while
Section~\ref{sec:deployability} shows the effect is masked entirely
under 36-byte text encoding.
The trade-offs of embedding vs a composite key are discussed in
Sections~\ref{sec:why-embed} and~\ref{sec:composite-bench}.

\subsection{Multi-tenant isolation}
The \texttt{multitenant} layout (Listing~\ref{lst:multitenant})
carries a 12-bit tenant enum and an 8-bit region enum. Tenant
scoping becomes a bit-range predicate on the primary key rather than
a join against a tenant table, and a row whose key-embedded tenant
disagrees with its session context is detectable without a join, not
prevented by the key alone. Still enforce authorization against the session
context; the key-embedded value is a routing hint any key holder can forge.
The region field supports data-residency assertions without a
secondary index. The allowed-tenant set is declared as $[1,8]$; a
wider set or a different constraint kind requires changing the
declaration, not the generator.

\begin{lstlisting}[caption={The \texttt{multitenant} layout. Only the constrained
           fields are declared; the generator is unchanged.},
  label={lst:multitenant}]
const multitenant: V8Layout = {
  name: "multitenant",
  fields: [
    { name: "tenant", offset:  0, length: 12, type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4,5,6,7,8] } },
    { name: "region", offset: 52, length:  8, type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4] } },
  ],
};
\end{lstlisting}

\subsection{Event sourcing}
The shipped \texttt{eventsourcing} layout pairs a 16-bit \texttt{stream} node at bit~0 with a 24-bit monotonic \texttt{seq} counter at bit~66, leaving 82 random bits. The layout is deliberately not timestamped: within one process, log position is carried by the counter, and the stream field separates concurrent writers, so an append-only log orders by primary key alone without a sequence server or a coordination round trip. Ordering rests on a single non-decreasing pair, the same one \texttt{dbkey} uses: the counter increments within a tick rather than being redrawn, and on exhaustion generation freezes until the clock advances, following RFC~9562 \S6.2, which prefers a bounded stall to a broken sort order. Both generation paths implement this: the pooled path clamps the tick and freezes inside the refill loop, and the compiled path emits the same clamp-and-freeze prologue into the generated function, so the guarantee does not depend on which backend the runtime selects. A timestamped variant of this layout is obtained by declaring a \texttt{timestamp-ms} field; that variant inherits the identical clamp and freeze-and-wait behaviour. Ordering is per-generator; cross-node total order still requires an external mechanism. Deployment envelope: single-writer/process logs only.

\section{Formal Analysis}
Rejection bets that a lucky whole-UUID draw arrives before an unlucky run; repair guarantees success by fixing only the fields that need it. The gap below quantifies that bet, and the entropy argument shows it costs nothing in randomness quality.

\subsection{Repair complexity: $O(k)$ versus an expected $64^k$ draws}
\label{sec:repair-complexity}

\noindent\emph{In plain terms: rejection sampling needs $\sim$69 billion tries for six constrained fields; GenoID succeeds on the first try. The exponential gap is against the general alternative, not against a per-layout hand-coded one.}

\textbf{Setup.} For $k$ constrained fields of bit-lengths $\ell_i$, each with $a_i$ valid values, rejection sampling succeeds with probability $\prod_i a_i / 2^{\ell_i}$, so the expected number of draws is $\prod_i 2^{\ell_i}/a_i$. Taking a representative tight constraint ($a_i=4$ admissible values in an $\ell_i=8$ bit field, a density of $2^{-6}$) gives $64^k$ expected draws ($6.9\times10^{10}$ for $k=6$), with a geometric tail and therefore no upper bound on any single run. The \texttt{shard} field of Listing~\ref{lst:dbkey} sits in this regime at $5/256$. The degenerate case $a_i=1$ is excluded: a field with a single admissible value is a constant and requires no sampling. \texttt{repairConstraints} (Algorithm~\ref{alg:repair}) is linear in $k$: it iterates the layout once, each branch is $O(1)$: an index-modulo lookup, an affine modulo, or a counter increment, so the pass has worst-case $O(k)$ cost. Both $|\text{allowed}_i|$ and $\ell_i$ are fixed by the layout declaration; treating them as constants yields $O(k)$. The function never redraws and never loops, eliminating rejection sampling's unbounded tail risk. The honest baseline for a fixed layout is per-field direct construction: draw a uniform index into the allowed set, draw uniform in-range values, increment the counter, and compose, equally $O(k)$, single-pass, bounded-tail, and exactly uniform with zero total-variation debt. Repair is not a faster sampler than this; it is the mechanism that lets one shared pass serve every declared layout without per-layout code, at the stated fibre debt ($m/2^\ell$ on allowed-set fields) and endpoint pile-up on range clamps. Where a single fixed layout is all that is ever needed, direct construction dominates and should be used; GenoID's claim starts at declared multi-field layouts whose admissible sets, bounds, and counters are repaired deterministically.

\subsection{Entropy preservation}
\label{sec:entropy}

A draw from a CSPRNG-filled pool is distributionally identical to a direct
CSPRNG call, so pooling is measure-preserving. Repair is deterministic, so
by the data-processing inequality $H(g(X)) \leq H(X)$: it can hold or
reduce entropy, never increase it. Pooled and unpooled variants pass NIST
identically (Section~\ref{sec:nist}), consistent with the former.

\subsection{Uniformity of constraint repair}
\label{sec:uniformity}

Let $A = (a_0, a_1, \dots, a_{m-1})$ be the admissible set in declaration order, $m = |A|$, and let $C_i = \left\lfloor (2^\ell - 1 - i)/m \right\rfloor + 1$ be the number of $\ell$-bit values congruent to $i$ modulo $m$. Index-modulo repair sends a raw value $v$ to $a_{v \bmod m}$, so the fibre of $a_i$ is exactly $C_i$. Total variation distance is bounded by
\[
  \|p - u\|_{\mathrm{TV}} \;\le\; \frac{m}{2^\ell}, \qquad
  \max_i |p(a_i) - 1/m| \;\le\; \frac{\lceil 2^\ell/m \rceil}{2^\ell},
\]
where $u$ is uniform on $A$; the second bound follows from the first because no admissible value can gain more than a whole excess class.

\textbf{Theorem (fibre sizes).} On the compiled path, which applies $A[v \bmod m]$ unconditionally, the probability of drawing $a_i$ is $C_i / 2^\ell$, and the repaired distribution is exactly uniform \emph{iff} $m \mid 2^\ell$.

The pooled path keeps an already-admissible value as itself before falling back to $A[v \bmod m]$, so it partitions the raw values differently. Writing $G_i = |\{a \in A : a \equiv i \pmod m\}|$, the fibre of $a_i$ on that path is $1 + C_i - G_i$. The two agree on every contiguous admissible set, and differ as soon as the set skips a residue class.

\textbf{Corollary (pooled-path uniformity).} On the pooled path the repaired distribution is exactly uniform \emph{iff} $m \mid 2^\ell$ and $G_i = 1$ for every $i$, i.e.\ the admissible set occupies every residue class exactly once.

Both conditions are satisfied by every layout this paper evaluates, which is why the measurement in Section~\ref{sec:evaluation} is path-independent for them. The conditions are also tight, and the two paths really do diverge when they fail. Take $m=2$, $\ell=2$, $A = \{0,2\}$: $m \mid 2^\ell$ holds, so the compiled path stays uniform at $(50\%, 50\%)$, whereas the pooled path folds the residue-1 draws onto $a_1 = 2$ and emits $(25\%, 75\%)$; the accompanying test suite pins both the prediction and the empirical split. This is the precise sense in which a declarative layout's field width and admissible set are correctness obligations on the author, not tuning parameters: a declaration that skips residue classes is still \emph{admissible} on every draw, but its per-value frequencies are path-dependent and the validator reports the residual bound rather than silently accepting it.

For \texttt{dbkey} ($m=5$, $\ell=8$), $256 \bmod 5 = 1$, so one residue class holds 52 raw values and the other four hold 51; with the contiguous set $A = \{1,2,3,4,5\}$ the class of index~0 (value~1) is the heavy one, giving $(52,51,51,51,51)$ preimages out of 256, a maximum per-value deviation of $(52 - 51.2)/256 \approx 0.31\%$ from uniform $51.2/256$, and a worst-case spread between classes of $(52-51)/256 = 0.39\%$. For \texttt{multitenant}, the region field ($m=4$, $\ell=8$) and the tenant field ($m=8$, $\ell=12$) both satisfy $m \mid 2^\ell$ with $G_i = 1$ throughout, so both are exactly uniform on either path; no multitenant field is declared at $\ell=12$ with $m=4$. The map is a surjection with near-equal fibres and involves no redraw, preserving the $O(1)$ per-field cost of Algorithm~\ref{alg:repair}.

The \textsc{range} branch clamps rather than folds, and is therefore not uniformity-preserving: draws outside $[\textit{min},\textit{max}]$ accumulate at the endpoints, with closed-form masses $P(\textit{out} = \textit{min}) = (\textit{lo}+1)/2^\ell$ and $P(\textit{out} = \textit{max}) = (2^\ell-\textit{hi})/2^\ell$ where $[\textit{lo},\textit{hi}]$ is the declared interval clipped to the $\ell$-bit field domain (\texttt{rangeClampMass} in \texttt{src/algo.ts}), so the total pinned mass is $(\textit{lo} + 2^\ell - 1 - \textit{hi})/2^\ell$. Neither layout evaluated here declares a range constraint; a layout that does should size the field so that out-of-range draws are rare, or declare an admissible set instead. The bound is measured directly: over four $(\ell,\textit{min},\textit{max})$ cells including the shipped conformance window ($2\times10^5$ seeded draws per cell), every measured endpoint mass matches its closed form to within $0.06$ percentage points ($4/4$ cells; \texttt{results/repair-grid.json}). The fibre prediction is also checked directly: over a grid of $(m,\ell)$ pairs ($m \in \{2,3,4,5,8\}$, $\ell \in \{3,4,8,12,16\}$, $2\times10^5$ seeded draws per cell), every measured frequency matches its closed-form fibre to within $0.3$ percentage points ($24/24$ cells; \texttt{results/repair-grid.json}).

\subsection{Bit allocation}
\label{sec:bit-allocation}

Declaring a field answers two questions at once: how wide it must be, and where
it sits. Width is an entropy question, a field holding one of five values
needs three bits, not eight, and every surplus bit comes out of the residual
entropy the collision guarantee depends on. Position is a locality question,
a field a query filters on costs more the deeper it sits, because every
comparison walks past it. The planner that shipped with earlier revisions
answered neither: widths were caller-declared and never checked against the
cardinality they must represent, and position was chosen by sorting fields into
three workload-role ranks and, inside a rank, by descending width.

\noindent\emph{Widths first.} A field whose domain contains $c$ values requires
$\lceil \log_2 c \rceil$ bits, so that is a hard floor, and it is the
entropy-minimising width because weighted depth is non-decreasing in every
width. A second constraint is new to this compiler: the residual random bits
$r$ must satisfy the collision target. For $n$ identifiers drawn with $r$
random bits the collision probability is bounded by
$1 - \exp(-n(n-1)/2^{r+2})$, so the smallest safe $r$ is
$\lceil \log_2\, n(n-1)\,/\,4\ln\frac{1}{1-\tau} \rceil$. Two million
identifiers at $\tau = 10^{-2}$ need 47 bits; at $\tau = 10^{-9}$ they need 70.
A declaration whose floors and required residual exceed the 122-bit payload is
refused with a reason naming the shortfall, rather than being silently
truncated.

\noindent\emph{Position next.} Weighted depth $D = \sum_i w_i (o_i + \ell_i)$,
weight times end-offset, summed over fields, is the comparison work a
range of queries performs. Treating each field as a job of length $\ell_i$
completing at $o_i+\ell_i$, this is exactly the single-machine
weighted-completion-time objective. By Smith's exchange argument~\cite{27}, $D$ is
minimised by ordering fields in non-increasing $w_i/\ell_i$: swapping an
adjacent inverted pair changes $D$ by
$\ell_a \ell_b (w_a/\ell_a - w_b/\ell_b) \le 0$. \texttt{planBitAllocation}
implements that order. The role-rank order is neither Smith order nor a special
case of it, and the difference is measurable.

The guarantee is stated exactly where it holds. The six reserved bits split the
free payload into the segments $[0,48)$, $[52,64)$, and $[66,128)$; Smith's
rule is exact on one unconstrained timeline, so the allocator is provably
optimal for any declaration whose fields fit inside a single segment, and misses
the optimum by at most a few percent when structure spills across a reserved
region. Every one of the five suboptimal instances in Table~\ref{tab:bit-allocation}
crosses bit~48, and no instance that stays inside $[0,48)$ is suboptimal.

The trade this makes explicit is linear in depth and logarithmic in risk
(Table~\ref{tab:bit-allocation}, E-A2): widening a declared field by one bit
costs about 95 units of $D$ and exactly doubles the collision probability. E-A3
plays the allocator back over the shipped \texttt{dbkey} declaration and finds
it already optimal, with the timestamp pinned at offset~0 and only two free
fields, a validation of the hand-written layout rather than a
disagreement. The one thing it gets wrong is width: the shard field is declared
at 8 bits for five admissible values, and $\lceil \log_2 5 \rceil = 3$ recovers
the five surplus bits as residual entropy.

Two limits are worth stating. Weighted depth is a proxy for comparison work, not
a measurement of query throughput; the database experiment in
Section~\ref{sec:composite-bench} is the closest empirical check and it measures
latency, not $D$. And nothing here infers the weight $w_i$ from a workload: the
caller supplies it, and mapping \texttt{DatabaseWorkloadProfile}'s read weight
and skew onto $w_i$ is left to the caller. The reduction to scheduling is not
new. Smith's rule is from 1956, so the contribution is the reduction
itself, the collision-safety constraint the compiler lacked, and the measurement
of what the role-rank order was costing.

\subsection{Closing the loop: workload-driven weights}
\label{sec:workload-planning}

The gap above is now closed end to end. \texttt{inferWorkload} recovers
field weights, roles, selectivity, and cardinality bounds from a query trace
instead of taking them as hand input: weights are access counts, roles follow
usage (range-filtered $\to$ partition, point-filtered $\to$ lookup), and
cardinality counts distinct observed values. \texttt{src/scripts/bench-workload.ts}
generates a seeded 10{,}000-query trace, infers the weights, and lets Smith
order place the hot field first; the hand baseline keeps region first. The
measured query is always the workload's hot field, run as PK range seeks on
200{,}000-row SQLite tables with SQL counts verified against a JS bit-decode.
Under a tenant-heavy mix the inference recovers weights of 7987 (tenant) and
1530 (region), the planner puts tenant first, and the tenant point query is one
PK range seek against the hand layout's four:
$3099\,\mu$s versus $14694\,\mu$s per lookup (means over 5 reps of 500
lookups, non-overlapping 95\% CIs), a $4.7\times$ win, with insert throughput
at parity on both engines (alternating timed reps; SQLite reps vary with host
load, PostgreSQL reps agree within 5\%). Under an inverted region-heavy mix the planner emits region-first,
coinciding with the hand layout, and the region probes show parity on both
engines (SQLite $5636\,\mu$s versus $5762\,\mu$s with overlapping CIs;
PostgreSQL $1.03\times$, CIs narrowly separated around a $3\%$ gap): convergence, not a win, which is the correct outcome when
the hand order is already optimal. The same loop runs on PostgreSQL (embedded PGlite~\cite{24}, BYTEA PK):
there both layouts tie on lookups ($1.02\times$, overlapping CIs), because
counting 25{,}000 matching rows in WASM execution dominates the 1-vs-4 seek
difference that the native SQLite executor exposes. The planning win
materializes where index access dominates row visits; on row-visit-dominated
engines the layout choice is free either way. The trace is synthetic but seeded and archived with its parameters
in \texttt{results/workload-planning.json}, so the loop, not the trace,
is the claim under test. A skewed trace is the favourable case by
construction; the Section~\ref{sec:composite-bench} result stands for the
neutral one.

\subsection{Microshard head-to-head}
\label{sec:microshard}

The closest public overlap is \texttt{microshard-uuid} (pip, v1.0.0): a fixed
RFC~9562 v8 layout with 54-bit microsecond timestamp, 32-bit shard, and 36
random bits, measured here through a bit-exact TypeScript mirror
cross-checked field-for-field against the Python implementation (version,
variant, shard, and timestamp all agree on fixed vectors). On the same
200{,}000-row SQLite setup, a tenant prune is one PK range seek for the
tenant-first GenoID layout against a full scan with in-app shard filtering
for microshard, whose shard straddles time bits and offers no SQL prefix:
$3446\,\mu$s versus $4383\,\mu$s (means over 5 reps of 500 lookups; CIs
nearly touch), a modest $1.3\times$ edge to the prunable layout, with full-ID
point lookups and inserts at parity on both sides. mirrored-throughput favours
GenoID ($2.2$M vs $0.14$M UUIDs/s in the TypeScript mirror; most of the gap is BigInt construction cost in the mirror rather than an architectural gap). The structural difference
appears under burst load: with the clock frozen and the shard fixed,
200{,}000 draws collide never for either layout, but at $2\times10^6$ draws
microshard shows 33 duplicates against an expected
$n^2/2\cdot2^{36}\approx29$ while the tick-keyed monotonic counter holds
GenoID at zero. The comparison isolates what each structure buys: GenoID
buys SQL prunability and counter-ordered bursts; microshard buys a fixed
layout with zero-lookup routing, at the price of birthday-bound bursts.

Within a single millisecond, the counter is predictable by design; this discloses emission order rather than reducing entropy, consistent with RFC~9562 \S6.2's recommendation that counter values need not be secret.

Base generation pools hold 256 entries and structured generation pools hold up to 1024 entries, independently repopulated per refill. An adversary who reads pool state predicts at most $\leq 1024$ future UUIDs per active generator, a bounded forward-secrecy window. Past buffers are overwritten, providing backward secrecy. Pool configuration can be tuned at runtime via \texttt{configurePools()}. Size the pool from an exposure budget: a pool of $W$ UUIDs exposes at most $W$ future identifiers per active generator (256 on the simple path, up to 1024 on the structured paths), i.e.\ a window of $W/R$ seconds at a sustained $R$ UUIDs/s (single-digit milliseconds at the Table~\ref{tab:throughput} rates); shrink $W$ to narrow the window at the cost of more frequent CSPRNG refills. Output is byte-identical at any pool size, so sizing trades only refill frequency against exposure.

\subsection{Composition correctness}
\label{sec:composition-correctness}
Over 1.5M structured-field checks on the shipped compiled-direct-v8 production path: 0 field-copy mismatches, 0 constraint violations, and 0 monotonicity violations (Table~\ref{tab:artifact-map}). This is the empirical counterpart to the by-construction correctness proof, measured end-to-end through \texttt{genStructuredGenoID(DBKEY\_Layout)} rather than lower-level primitives.

\subsection{Repair versus rejection cost}
\label{sec:repair-vs-rejection}

A sweep over constraint density $d$ and field count $k$ (40 cells)
separates the two strategies structurally. Measured repairs per
identifier follow $k(1-d)$ at every cell, converging to exactly $k$ as
$d \to 0$ and to $k/2$ at $d=0.5$: \texttt{repairConstraints} performs
one bounded operation per constrained field and none that depend on the
drawn value. At the low-density end of each block, per-identifier cost is
$\approx\!0.7$--$1.0\,\mu$s per constrained field at $d=1/64$ across
$k \in \{1,2,3,4,6\}$ ($0.8$/$2.0$/$2.8$/$4.1$/$4.1\,\mu$s totals;
\texttt{results/rejection-sweep.json}), rising with $k$; absolute timings
carry the warm-up ordering effect noted in Section~\ref{sec:validity}.

Rejection's expected trial count follows $d^{-k}$ and becomes infeasible to measure beyond $k=3$ at low density. At $d=1/64$, the representative constraint of Section~\ref{sec:repair-complexity}, the sweep reproduces $64^k$ exactly for $k=3,4,6$ ($2.62\times10^{5}$, $1.68\times10^{7}$, $6.87\times10^{10}$).

The asymptotic advantage is real but bounded, and we state where it
begins. Rejection is faster at loose constraints and low field counts:
for $k=1$ the crossover falls between $d=0.016$ and $d=0.031$ (adjacent
measured densities), for $k=2$ between $0.0625$ and $0.125$, and for
$k \geq 3$ between $0.25$ and $0.5$ (\texttt{results/rejection-sweep.csv}):
the boundary moves toward higher density as $k$ grows, because repair cost
is flat in $d$ while rejection is exponential in $k$. A layout with a single loosely constrained field is
better served by rejection. GenoID's guarantee is that cost never depends
on the draw, which matters when constraints are tight, when fields are
many, or when unbounded tail latency is unacceptable.

\subsection{Collision and uniformity}
Per-field uniformity is measured directly rather than inferred from whole-UUID batteries, since an 8-bit field's deviation is invisible inside 122 bits under NIST monobit. Over $10^8$ \texttt{dbkey} draws on the shipped compiled path, one shard value ($1$) appears at $52/256$ and the other four at $51/256$, matching the closed-form index-modulo prediction of Section~\ref{sec:uniformity}; the maximum absolute deviation from the predicted fibre frequency is $0.012$ percentage points, which is $2.9$ of that cell's own binomial sampling standard deviation ($0.004$ pp at $n=10^8$). Across all 17 tested cells the family-wise assessment gives max-$|z|=2.90$ against a Bonferroni critical value of $2.97$ at family-wise $\alpha=0.05$ (\v{S}id\'ak $2.97$, Bonferroni $p=0.064$), i.e.\ consistent with sampling noise once the 17-fold multiple comparison is accounted for. \texttt{results/shard-histogram-100m.maxz.json} records that assessment, computed from the archived per-cell counts with no new draws. The \texttt{multitenant} tenant ($m=8$ at $\ell=12$) and region ($m=4$ at $\ell=8$) fields are uniform to within $0.008$ pp, consistent with $m \mid 2^{\ell}$ making the partition exact. No admissible value ever falls outside its declared set across $2\times10^8$ draws. Collision expectations for \texttt{dbkey} use the 50 random-payload bits (50\%-collision bound $3.95\times10^7$; $\approx\!10^{10}$ within-tick with the 16-bit same-tick counter). We report agreement with the predicted distribution rather than a goodness-of-fit test against strict uniformity: at $n=10^8$ even the analytically expected $\leq 0.39\%$ per-value deviation would cause chi-square against uniform to reject by design, so rejection is inevitable when testing against perfect uniformity. As a negative control, \texttt{Math.random} (insecure, runtime-native PRNG) passes the collision test in all nine CI environments under the same protocol, confirming that the 1M-draw collision gate has no discriminating power against a low-entropy source; only the analytical uniformity bound and NIST battery separate quality from speed. \texttt{results/shard-histogram-100m.json} records the raw counts, per-cell binomial standard deviations, commit SHA, host, and elapsed time.

\subsection{NIST SP 800-22 and dieharder}
\label{sec:nist}
The full 15-test NIST SP~800-22 battery was run on all three structured layouts (Block Frequency implemented per SP~800-22 \S2.2 and cross-checked against reference vectors (custom implementation noted as a single point of failure); the \texttt{nist80022} package provides the remaining tests, fanned across layouts by \texttt{src/scripts/nist-full-battery.py}). On fresh $10^7$-bit exports of the random-field payload per layout (200k/98k/122k UUIDs), all 123 reported p-values (41 per layout, including the 8 Random Excursions states and 18 Random Excursions Variant states) satisfy $p \geq 0.01$ (unconditional pass probability $\approx 0.29$ under the null); machine-readable results are archived in \texttt{results/nist-sp800-22-results.json}. Because the battery reports 123 p-values at $\alpha=0.01$, marginal values below threshold are expected by chance ($\approx 1.2$ per full run): across five independent draws (615 p-values) we observe 7 failures for an empirical $1.1\%$ rate, with draws at 123/123, 120/123, 123/123, 120/123, and 122/123. Every failed draw is archived with its bit-stream provenance in \texttt{results/nist-draws/} (draws 2--5; the clean head draw's bit stream is archived with \texttt{results/nist-sp800-22-results.json}); full per-draw tables are in the appendix. no test fails in a majority of draws, and the single repeat (Spectral on multitenant, twice in five draws) is expected under the null: the per-test repeat probability is $\approx 0.001$, giving $\approx 11\%$ for at least one repeat across 123 test slots. A targeted follow-up ran the Spectral test alone over 30 fresh $10^6$-bit exports per arm (multitenant suspect, dbkey layout control, unstructured pooled control): fail rates 1/30, 0/30, 1/30, consistent with Type-I noise rather than a layout-induced spectral peak at this lower-power stream length (a matched $10^7$-bit repeat remains future work). Each layout contributes five streams, where NIST guidance prefers $\geq 100$; the battery therefore reads as evidence of no structural bias on the pooling path, not a certification. (SP~800-22 has been withdrawn by NIST and its planned revision explicitly rejects the suite's use for assessing cryptographic generators~\cite{2}; we report the result as a sanity check on the pooling path, not as evidence of security.) A curated dieharder subset (diehard $+$ STS, \texttt{-d 0 2 7 8 10 15 100 102}, 12.5\,MB per generator per trial, 5 trials, no file rewind; methodology in \texttt{sources/reproducibility.md}~\S3) reports a modal PASS on all 152 test rows across four arms (v4, rawv8, pooled genoid, struct-dbkey; \texttt{results/dieharder-results.md}). This is a CI-budget curation over payload generators, not a full-battery run, and it covers the unstructured and \texttt{dbkey} payload paths only.

Two results run against us. \texttt{snowflake} is faster in all nine environments, by up to $\approx 2\times$; it is a 64-bit time-and-sequence integer rather than a 122-bit UUID, and it collides once its sequence wraps, so the comparison is across guarantee classes rather than within one. \subsection{Ablation}
\label{sec:ablation}
A prototype layout compiler emitting inlined per-layout code yields a geometric-mean $0.56\times$ across the nine environments: near parity on Bun ($1.01$--$1.10\times$, n.s.\ on two of three), small but significant regressions on Deno ($0.92$--$0.95\times$), and a large regression on Node~22 ($0.14$--$0.22\times$; Table~\ref{tab:paired}). The compiler therefore buys nothing on the refreshed matrix, and the interpreted repair pass remains the cheaper path on every runtime; further work should target the pooling and string-formatting paths, and the Node code-generation regression, instead. The two-parent design itself is load-bearing: a single-parent ablation reaches only $0.158\times$ of production throughput with identical collision (0) and uniformity ($\leq 0.006$) behaviour (\texttt{results/structured-evidence.json}, E7), so the second parent buys a $6.3\times$ speedup, not quality.

\subsection{Additional deployability checks}
\label{sec:deployability}
Concurrent generation shows 0 cross-worker collisions. A SQLite B-tree index benchmark (500K rows, clustered storage, 64-byte payloads) shows the structured arm inserting at $90.3$K rows/s [89.9--90.7K] against $61.5$K for UUIDv7 and $7.0$K for UUIDv4, with on-disk density nearly identical across arms ($0.074$--$0.077$ pages/row, \texttt{pg\_uuid\_v8} an outlier at $0.116$); per the harness note, SQLite repacks pages so on-disk size diverges less than production InnoDB, and the partition differentiator is storage plus write amplification rather than read latency. TEXT-stored (36-byte) keys would mask the ordering effect entirely. A cross-browser Playwright test (Chromium, Firefox, WebKit) reports 0 errors and 0 collisions.

\subsection{Cross-language reproducibility}
\label{sec:cross-lang}

To turn the portability claim into a checkable artifact, the composition core was reimplemented in Rust and verified against golden vectors from the TypeScript reference. Every repair branch is total and tie-free (index-modulo has no ambiguous outputs), so byte-identity across languages is a constructive property of the algorithm rather than an accident of hash-map iteration order. A xorshift128+ PRNG with fixed seed and fixed \texttt{Date.now()} produce 1000 UUIDs per layout across all three structured layouts, then diffed byte-for-byte against committed golden files, achieving zero mismatches across $3\times1000=3000$ UUIDs.

To establish that the vectors discriminate rather than merely agree, the check re-runs against deliberately broken semantics, and CI fails unless the breakage is detected. Shifting the index-modulo repair by one position fails \texttt{dbkey} (994/1000) and \texttt{multitenant} (1000/1000) while leaving \texttt{eventsourcing} and \texttt{conformance}, which declare no admissible-set constraint, untouched (0/1000 each); the six clean \texttt{dbkey} draws are ones whose raw values were already admissible, where repair is idempotent by design and any repair variant agrees. Freezing the tick-keyed counter instead of incrementing it fails \texttt{dbkey} (999/1000) and \texttt{eventsourcing} (999/1000) and leaves \texttt{multitenant} and \texttt{conformance}, which declare no counter, untouched (0/1000 each); the single agreement per run is the first UUID, which both paths seed from the same draw. Each layout is sensitive to exactly the constraint kinds it declares, and the per-layout mismatch counts are printed by the check itself.

The vectors were regenerated after the repair and counter algorithms changed during development; on re-verification the prior Rust port had diverged on both, a divergence a prose specification would not have surfaced. The vectors are checked into \texttt{golden/} and verified in CI on every push, serving as an executable specification for any future port.

In production, each port draws from its own OS CSPRNG; the seeded byte stream exists only for cross-language verification. Different buffering in a Rust port would be no less correct for producing different byte sequences.

\section{Related Work}
\label{sec:related-work}
\subsection{UUID standards: RFC 4122 to RFC 9562}
UUIDs originated as RFC~4122 (versions~1--5), obsoleted by RFC~9562 (2024), which adds versions~6, 7, and~8~\cite{4}. UUIDv4 carries 122 CSPRNG bits but lacks order; UUIDv7 prepends a 48-bit timestamp for index locality~\cite[\S5.7]{4}; UUIDv8 is explicitly experimental, with the RFC providing no creation algorithm for its 122 bits~\cite[\S5.8]{4}; its Appendix~B illustrates custom v8 algorithms without prescribing generation, confirming the standard leaves the design space open rather than unoccupied.
\subsection{Sortable and structured identifiers}
RFC~9562 surveyed sixteen prior implementations~\cite{4}. Representative members: ULID~\cite{5} (48-bit timestamp + 80-bit randomness), KSUID~\cite{6} (32-bit timestamp + 128-bit randomness), Snowflake~\cite{7} (timestamp $|$ worker $|$ sequence), TypeID~\cite{8} (typed prefix over UUIDv7), and COMBGUID-style sequential GUIDs (cf.\ the GUID-as-PK cost discussion~\cite{9}). MongoDB ObjectId (timestamp\,|\,machine\,|\,pid\,|\,counter, 2009) is the canonical embedded-structure precedent; GenoID is its declarative generalization to multi-field v8 layouts. Time-ordered identifiers improve database behavior~\cite{9}, with academic comparisons of UUIDv4/v7/ULID for distributed systems~\cite{10}. This is a well-explored field limited to fixed, hand-coded layouts; to our knowledge, no source documented through September 2026 offers a declarative layout language with per-field repair for multi-field v8 composition over allowed-set, range, and monotonic constraints.
\subsection{Steganographic UUIDs: closest prior art}
\texttt{pg\_uuid\_v8}~\cite{11}, a PostgreSQL C extension (PGXN, May~2026), is the closest prior art. It generates v4-compatible UUIDs with an embedded microsecond timestamp (XOR), recoverable by extraction function. GenoID differs: \texttt{pg\_uuid\_v8} offers one fixed stego layout with no multi-field abstraction or repair, while GenoID provides a declarative, multi-field DSL and constraint-guided repair as a portable library, published for the Node/Bun/Deno ecosystem.

\subsection{Closest contemporary overlap}
\texttt{microshard-uuid}~\cite{14} is the nearest deployable overlap: a public RFC~9562 v8 with a fixed 54-bit microsecond timestamp, 32-bit shard, and 36 random bits, advertising zero-lookup routing with extensions for SQLite~\cite{22}, PostgreSQL, MySQL~\cite{23}, DuckDB~\cite{25}, and ClickHouse~\cite{26}. It is a fixed layout, not a layout language: there is no per-field admissibility vocabulary, no repair policy, and no random-bit budget that varies by workload. GenoID concedes the fixed-layout case entirely; its claim starts where \texttt{microshard-uuid} stops, at declared multi-field layouts whose admissible sets, bounds, and counters are repaired deterministically with a stated total-variation bound.

\subsection{Constrained generation and repair lineage}
The generic lineage is older and stronger than the UUID literature. Property-based testing compiles executable properties into generators~\cite{15}; Claessen, Dureg{\aa}rd, and Pa{\l}ka derive random data satisfying a Boolean predicate while targeting uniformity~\cite{16}; LaFontaine et al.\ repair incomplete generators from type and coverage information~\cite{17}; Goldstein et al.\ synthesise generators with guarantees~\cite{18}. The formal distinction is scope: those systems solve arbitrary predicates or synthesise generators from proof obligations. GenoID does neither. It projects one fixed-width random field into one declared admissible set, with no predicate solving and no distribution-preservation claim beyond the fibre bound of Section~\ref{sec:uniformity}. ``Constraint-guided repair'' names that projection, not a general constrained-generation result.

\subsection{Database-locality alternatives}
Embedding is not the only route to locality. CockroachDB hash-shards indexes to spread sequential writes while keeping a logical partition key~\cite{19}; TiDB \texttt{AUTO\_RANDOM} randomises integer primary keys with shard bits~\cite{20}; SQL Server's \texttt{NEWSEQUENTIALID} issues process-ordered GUIDs for sequential index behaviour~\cite{21}; and expression or covering indexes extract queryable structure from plain values without touching the key format. GenoID's bet is narrower: when the key itself must carry routing so a partition prunes with no secondary index, embedding wins (Section~\ref{sec:composite-bench}); where it need not, an expression index over the plain key is the better-supported answer, but measured on the same rig it is not the cheaper one: it carries $1.93\times$ the storage and $2.07\times$ lower insert throughput of embedding for lookup parity ($1.04\times$), so the index trades throughput for tooling, not for savings.

On throughput, prior work amortizes CSPRNG draws via pooling~\cite{12}, and PostgreSQL~18 ships a native \texttt{uuidv7()}~\cite{13}; GenoID adopts the same principle with a 256-UUID pool.

\section{Threats to Validity}
\label{sec:validity}
We disclose these openly, ranked by expected reviewer pressure.

\textbf{External validity.} Rust reimplementation produces byte-identical output across 3000 seeded UUIDs and three layouts. Performance portability remains future work. Benchmarks run on shared CI runners; numbers are relative comparisons. No sharded-cluster routing experiment: cross-node dispatch cost, resharding cost, and cross-node clock-skew behavior are future work; routing claims rest on the single-key bit-mask mechanism.

\textbf{Construct validity.} NIST PASS/FAIL is necessary but not sufficient for security; Section~\ref{sec:security} provides a threat model and entropy accounting.

\textbf{Run-to-run stability.} The SQLite composite-key lookup measurement is the least stable quantity in this paper: the offset-56 versus offset-52 lookup difference reversed direction three times across four repeated runs of the same experiment ($+14\%$, $-2\%$, $+4.7\%$, $+4\%$), so we make no claim for it and report only the direction every arm agrees on. Insert throughput carried a similar instability in an earlier experiment, where one of three runs was uniformly $1.3$--$2.5\times$ slower under background load; the composite-key table above reports ten trials on one host, and the per-trial arrays in \texttt{results/db-sqlite-composite.json} let a reader re-check that no trial is an outlier.

\textbf{Internal validity.} Benchmark confounds are mitigated by mean $\pm$ SD over 10 trials with 95\% CI and Welch $t$-tests. Two implementation bugs (a byte-consumption mismatch in \texttt{eventsourcing}'s \texttt{node}-typed field and a missing seed-state reset) were caught by the test suite before publication. A dead-code-elimination (DCE) hazard in the timing loop was identified and corrected after early throughput runs: an unconsumed loop elides the pure-JavaScript generators' work, inflating measured rates by roughly $2\times$ while leaving native \texttt{crypto.randomUUID()} unchanged; every number in Table~\ref{tab:throughput} post-dates the correction, confirmed by consuming each generated value at a sink (\texttt{.codePointAt(0)}) that the JIT cannot prove is a no-op. NIST runs unconditionally; dieharder is a CI-budget curation. The SQLite composite-key benchmark (Section~\ref{sec:composite-bench}) revealed a between-run variance component not captured by within-run CIs; we exclude a run when every arm is $>1.3\times$ slower than the median run (post-hoc rule adopted after observing the slow run; the excluded per-trial arrays are archived alongside the kept runs). One of three runs met the rule and is excluded; the kept-run headline ratio is $3.1\times$ ($22.72$\,ms embedded against $7.38$\,ms composite shard scan, Table~\ref{tab:composite}), and because the rule fires only when every arm slows by the same factor, the exclusion leaves the ratio essentially unchanged. Absolute per-identifier times in the density sweep (Section~\ref{sec:repair-vs-rejection}) carry a warm-up ordering effect; the repair-count and trial-count results, on which the analysis rests, are order-independent.

\textbf{Runtime portability.} The refreshed nine-environment matrix no longer shows a Node-specific penalty on the interpreted structured path: it runs at $0.70$--$1.58\times$ of unstructured base on Node~22 against $0.72$--$0.91\times$ on Bun and Deno, consistently across Linux, macOS, and Windows, so the earlier boxed-\texttt{BigInt} hotspot attribution for the repair pass is superseded on current toolchains and is not repeated here. The penalty has moved to the compiled path instead: the layout compiler regresses to $0.14$--$0.22\times$ of the interpreted path on Node~22 while holding near parity on Bun and small deficits on Deno (Table~\ref{tab:paired}), a code-generation regression whose cause is under investigation. A reader deploying on Node~22 should therefore ship the interpreted structured path and benchmark before assuming any single figure transfers; the standalone portability probe on Node v26.13 (V8 14.6) measures $0.69\times$ of base throughput (95\% CI $[0.60, 0.79]$, 20 reps of 200k UUIDs; \texttt{results/node-portability.json}), consistent with the refreshed matrix range.

\textbf{Conclusion validity.} Throughput comparisons use Welch $t$-tests. ``0 collisions'' is reported alongside the birthday-bound expectation.

\textbf{Layout identity.} Pool validation, pool state, and compiled-generator caches are keyed by canonical structure hash, with a fail-closed guard: registering a layout whose name matches a previously registered but structurally different layout throws instead of sharing state. Layout names are therefore a human label over a structural identity, and reusing a name for a different field structure is a misuse, not a supported migration path.



\section{Conclusion and Future Work}
RFC~9562 leaves version~8's 122 bits undefined; GenoID fills them with a declarative, portable algorithm. Its core contribution is the \texttt{V8Layout} abstraction: typed, constrained multi-field composition with a single shared repair pass, validated through per-field uniformity at $10^8$ scale, an adversarial security analysis, and a cross-language reproducibility check. The measured $2.8$--$12.9\times$ throughput advantage over the closest prior art is a secondary result; the primary result is a framework for making shard, tenant, and sequence identity a property of the key itself, with proven $O(k)$ repair cost and the total-variation bound $m/2^\ell$ on allowed-set repaired fields.
