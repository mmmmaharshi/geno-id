\begin{abstract}
Standard UUID generators cannot embed application-defined structure (a shard, a tenant, or a monotonic counter) inside a standards-compliant identifier without paying rejection sampling's exponential cost. RFC 9562 makes this gap explicit: version 8 reserves 122 bits for exactly this purpose but defines no algorithm to fill them. We close this gap with GenoID, a declarative composition framework that produces valid v8 UUIDs from arbitrary constrained fields at $O(k)$ cost, against rejection sampling's $O(64^k)$ expected cost under tight constraints, with a proven $m/2^\ell$ uniformity bound on every repaired field, measured throughput $2.0$--$6.7\times$ that of the closest prior art across nine runtime environments, and byte-identity across an independent Rust reimplementation. The design is backed by formal complexity and entropy accounting and an explicit adversarial security analysis that separates GenoID's architectural contribution from the CSPRNG-inherited randomness quality beneath it. By making shard, tenant, and sequence identity a declarative property of the key itself, GenoID targets the data-systems layer directly.
\keywords{distributed data systems, sharding, UUID, RFC 9562}
\end{abstract}

\section{Introduction}

Imagine ten database servers where each record's ID must reveal which one owns it. RFC~9562's v8 UUID reserves 122 bits for application-defined structure but specifies no algorithm to fill them. GenoID is that missing algorithm: instead of rejection sampling's $O(64^k)$ draws, it produces correct keys on the first try in $O(k)$ work.

Existing UUIDs fall short: v4 carries no structure, v7 fixes one timestamp layout, and \texttt{pg\_uuid\_v8} embeds an encrypted timestamp with no multi-field composition. Structure in the key is not always the right choice --- a composite key is simpler whenever the identifier never leaves the database --- and Section~\ref{sec:why-embed} states the conditions under which it is, and Section~\ref{sec:composite-bench} quantifies the cost of the alternative. GenoID declares field structure once as a \texttt{V8Layout} and satisfies it by deterministic repair, drawing from pre-populated CSPRNG pools to amortize entropy cost.

\noindent\textbf{Contributions.}
\begin{itemize}
    \item A declarative RFC~9562 v8 layout abstraction for typed, constrained fields.
    \item A pooled generation architecture that amortizes CSPRNG draws, entropy-neutral by construction.
    \item Constraint-guided repair: $O(k)$ per UUID vs $O(64^k)$ rejection sampling.
    \item Proven $m/2^\ell$ uniformity bound on repaired constrained fields, exactly uniform when $m \mid 2^\ell$.
    \item An adversarial security analysis disclosing the bounded forward-secrecy window and by-design metadata leakage of structured layouts.
    \item Validation across per-field uniformity at $10^8$ scale (matching the closed-form $m/2^\ell$ bound to $\pm0.01$ percentage points), NIST and dieharder batteries, and multi-runtime throughput benchmarks, with limitations disclosed openly.
\end{itemize}

\section{Design}
\label{sec:design}
Think of a UUID's 122 free bits as a form with labeled blanks: timestamp, shard from a small set, monotonic counter. GenoID lets a developer declare that form once and fills every blank correctly on every call.

\medskip
\noindent\emph{Example:} a \texttt{dbkey} UUID for shard~3 at time~$t$: the first 48 bits read as $t$, the shard byte reads 3, a router extracts ``shard~3'' directly from the key. Remaining bits are random.

\subsection{Declarative layout}
\label{sec:layout}
A \texttt{V8Layout} declares ordered \texttt{V8Field}s with bit offset, length, type, and optional constraint.

\begin{lstlisting}[language=Java,
  caption={The \texttt{dbkey} layout declaration. Bit ranges 48--51
           (\texttt{ver}) and 64--65 (\texttt{var}) are never declared:
           \texttt{completeLayout} reserves them per RFC~9562 and fills
           every remaining undeclared range with random filler.},
  label={lst:dbkey}]
const dbkey: V8Layout = {
  name: "dbkey",
  fields: [
    { name: "timestamp", offset:  0, length: 48,
      type: "timestamp-ms" },
    { name: "shard",     offset: 52, length:  8,
      type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4,5] } },
    { name: "counter",   offset: 66, length: 16,
      type: "counter",
      constraint: { kind: "monotonic" } },
  ],
};
\end{lstlisting}

Listing~\ref{lst:dbkey} is the complete specification: no generation code is written per layout, and the same \texttt{repairConstraints} pass (Algorithm~\ref{alg:repair}) serves every declaration. Substituting \texttt{allowed: [1..5]} with a 12-bit tenant enum and an 8-bit region enum yields the \texttt{multitenant} layout without touching the generator. (The listing retains offset~52 for \texttt{shard} as the measured baseline; Section~\ref{sec:composite-bench} shows offset~56 yields a modest lookup improvement and is the recommended alignment.)

\subsection{Implementation: pooled CSPRNG generation}
\label{sec:pooled-gen}
A 256-entry pool is populated from the OS CSPRNG on first use and
refilled in full when exhausted. Each call draws one 128-bit value from
the pool; the single shared \texttt{repairConstraints} pass
(Algorithm~\ref{alg:repair}) then fixes any constrained field that falls
outside its admissible set.

\subsection{Constraint-guided repair}
\label{sec:repair}

\begin{algorithm}[!ht]
\caption{\texttt{repairConstraints}: single-pass constraint satisfaction}
\label{alg:repair}
\begin{algorithmic}[1]
\Require Layout $L$ with fields $f_1..f_n$; candidate 128-bit value $u$
\Ensure  $u'$ satisfying every constraint declared in $L$
\Statex
\For{each $f \in L.\textit{fields}$ with $f.\textit{constraint} \neq \textsc{null}$}
  \State $v \gets \textsc{ExtractBits}(u,\, f.\textit{offset},\, f.\textit{length})$
  \State $c \gets f.\textit{constraint}$
  \If{$c.\textit{kind} = \textsc{allowed}$}
    \State $v' \gets
           \begin{cases}
             v & v \in c.\textit{allowed} \\
             c.\textit{allowed}[\,v \bmod |c.\textit{allowed}|\,] & \text{otherwise}
           \end{cases}$
            \Comment{$O(1)$}
  \ElsIf{$c.\textit{kind} = \textsc{range}$}
    \State $v' \gets \max\bigl(c.\textit{min},\ \min(v,\, c.\textit{max})\bigr)$
            \Comment{$O(1)$}
  \EndIf
  \State $u \gets \textsc{WriteBits}(u,\, f.\textit{offset},\,
          f.\textit{length},\, v')$
\EndFor
\State \Return \textsc{SetVersionVariant}(u)
        \Comment{RFC~9562 \S4.2}
\end{algorithmic}
\end{algorithm}

Every branch assigns $v'$ unconditionally, so the loop body cannot fail and the procedure contains no backward jump: it executes exactly $k$ iterations for $k$ constrained fields, independent of the drawn value. Correctness is by construction: each branch's codomain is the constraint's satisfying set: 0 violations, not ``near 0.'' Monotonic fields are handled by the pool refill path's tick-keyed counter logic before \texttt{repairConstraints} is called.

Figure~\ref{fig:pipeline} shows a single repair: a drawn candidate whose \texttt{shard} field reads 7 is mapped to the admissible value 3.

With $\ell_c=16$ and $g=1$, reseeding leaves at least $2^{15}=32768$ increments per millisecond. At 3040~UUIDs/ms the counter advances once per UUID, yielding a $\sim10\times$ margin before the rollover path. Per-generator state is isolated; concurrent generators require no locks.

\section{Applications}
\label{sec:applications}
Each use case below declares one layout and reads one field; no
generation code is written per application.

\subsection{Why embed structure in the key?}
\label{sec:why-embed}

The obvious alternative to embedding a shard in the identifier is to keep
it beside the identifier: a composite key
$(\textit{shard\_id}, \textit{uuid})$, or a separate indexed column. That
design is simpler than anything in this paper, and it is better on three
axes we do not contest. Resharding becomes a column update rather than a
layout migration and a dual-read window. The identifier retains all 122
random bits, so none of the entropy accounting in
Section~\ref{sec:entropy-accounting} applies. And the shard count is not
bounded by a field width fixed at declaration time.

Embedding wins in one specific circumstance: when the identifier must
cross a boundary that carries a single value. A URL path segment, a cache
key, a queue partition key, a log line, or a foreign key in a system one
does not control each admit one identifier, not two. A composite key
crossing such a boundary degrades to string concatenation --- an ad-hoc,
unvalidated encoding of precisely what \texttt{V8Layout} specifies
formally --- and the concatenated form is no longer a UUID, forfeiting
the native 16-byte column type, its index representation, and the library
and tooling support that RFC~9562 conformance carries.

A second, narrower benefit is integrity. When the tenant is a projection
of the key rather than a neighbouring column, a row whose key and session
context disagree is impossible by construction rather than merely
detectable: two columns can drift, one cannot.

We therefore position GenoID for stable shard and tenant sets whose
identifiers escape the database, and not for elastic partitioning behind
a boundary the application fully controls.

\subsection{Cost of embedding versus a composite key}
\label{sec:composite-bench}

Section~\ref{sec:why-embed} claims a composite key does not help a lookup
arriving without its shard. We test this against four alternatives over
one workload, all arms using the same timestamp-sorted 128-bit identifier
under \texttt{WITHOUT ROWID} clustered storage, so the only variable is
where the shard resides.

Given a primary key $(\textit{shard},\textit{id})$, a lookup by
identifier alone cannot seek the index: \texttt{EXPLAIN QUERY PLAN}
reports \texttt{SCAN}, and latency grows linearly in table size against
the embedded key's logarithmic growth. Answering such a query therefore
requires a secondary index on \textit{id}, and that is the comparison
that matters, since any deployment facing this access pattern would add
one.

The secondary index is what embedding avoids. It carries $1.98\times$ the
storage per row ($54.5$ against $27.5$ bytes) and sustains $1.95\times$
lower insert throughput, while still resolving lookups $1.45\times$
slower --- resolution descends the secondary index and then the primary
key, where the embedded form descends once. Embedding serves both access
paths with a single index.

Two comparisons show no difference and we report them as such: insert
throughput is indistinguishable between the embedded key and an
unindexed composite key, and point-lookup latency is indistinguishable
between the embedded key and a concatenated text key. Concatenation
nonetheless costs $1.88\times$ the storage and $1.37\times$ lower insert
throughput, and is no longer a UUID, forfeiting the native 16-byte column
type and RFC~9562 tooling. Declaring the shard at a byte-aligned offset
(56 rather than 52) yields a further $14\%$ on lookup, since the field
becomes extractable by a single-byte predicate --- a design rule the
layout validator can enforce.

We claim no advantage on shard-major scans, where the composite key's
leading column is the better structure.

\subsection{Sharded databases}
Listing~\ref{lst:dbkey} embeds the owning shard directly in the key.
A router extracts bits 52--59 and dispatches without consulting a
shard map: routing becomes a bit-mask and a comparison, replacing a
hash computation and a ring lookup under consistent hashing, and
removing the coordination needed to keep a shard map current across
application nodes. The 48-bit timestamp prefix orders keys by emission
time; on 16-byte binary storage this yields the insert and lookup
behaviour of Table~\ref{tab:composite}, while
Section~\ref{sec:deployability} shows the effect is masked entirely
under 36-byte text encoding.
The trade-offs of embedding vs a composite key are discussed in
Sections~\ref{sec:why-embed} and~\ref{sec:composite-bench}.

\subsection{Multi-tenant isolation}
The \texttt{multitenant} layout (Listing~\ref{lst:multitenant})
carries a 12-bit tenant enum and an 8-bit region enum. Tenant
scoping becomes a bit-range predicate on the primary key rather than
a join against a tenant table, and a row whose key-embedded tenant
disagrees with its session context is impossible by construction,
since the key is the single source of truth.
The region field supports data-residency assertions without a
secondary index. The allowed-tenant set is declared as $[1,8]$; a
wider set or a different constraint kind requires changing the
declaration, not the generator.

\begin{lstlisting}[language=Java,
  caption={The \texttt{multitenant} layout. Only the constrained
           fields are declared; the generator is unchanged.},
  label={lst:multitenant}]
const multitenant: V8Layout = {
  name: "multitenant",
  fields: [
    { name: "tenant", offset:  0, length: 12, type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4,5,6,7,8] } },
    { name: "region", offset: 52, length:  8, type: "shard",
      constraint: { kind: "allowed", allowed: [1,2,3,4] } },
  ],
};
\end{lstlisting}

\subsection{Event sourcing}
Pairing a 48-bit timestamp with a monotonic counter yields
identifiers that sort in emission order within a node, with the
counter breaking ties inside a single millisecond. An append-only
log therefore orders by primary key alone, without a sequence
server or a coordination round trip. Ordering rests on a single
non-decreasing pair: the timestamp is clamped to
$\max(\text{clock}, \textit{last tick})$, and the counter increments
within a tick rather than being redrawn. A backwards clock therefore
yields the previous tick with an incremented counter --- monotonic by
construction --- rather than an out-of-order key. Counter exhaustion
within a tick freezes generation until the clock advances, following
RFC~9562 \S6.2, which prefers a bounded stall to a broken sort order.
Ordering is per-generator; cross-node total order still
requires an external mechanism.

\section{Formal Analysis}
Rejection bets that a lucky whole-UUID draw arrives before an unlucky run; repair guarantees success by fixing only the fields that need it. The gap below quantifies that bet, and the entropy argument shows it costs nothing in randomness quality.

\subsection{Repair complexity: $O(k)$ versus $O(64^k)$}
\label{sec:repair-complexity}

\noindent\emph{In plain terms: rejection sampling needs $\sim$69 billion tries for six constrained fields; GenoID succeeds on the first try. The exponential gap is against the general alternative, not against a per-layout hand-coded one.}

\textbf{Setup.} For $k$ constrained fields of bit-lengths $\ell_i$, each with $a_i$ valid values, rejection sampling succeeds with probability $\prod_i a_i / 2^{\ell_i}$, so the expected number of draws is $\prod_i 2^{\ell_i}/a_i$. Taking a representative tight constraint ($a_i=4$ admissible values in an $\ell_i=8$ bit field, a density of $2^{-6}$) gives $64^k$ expected draws ($6.9\times10^{10}$ for $k=6$), with a geometric tail and therefore no upper bound on any single run. The \texttt{shard} field of Listing~\ref{lst:dbkey} sits in this regime at $5/256$. The degenerate case $a_i=1$ is excluded: a field with a single admissible value is a constant and requires no sampling. \texttt{repairConstraints} (Algorithm~\ref{alg:repair}) is linear in $k$: it iterates the layout once, each branch is $O(1)$ --- an index-modulo lookup, an affine modulo, or a counter increment --- so the pass has worst-case $O(k)$ cost. Both $|\text{allowed}_i|$ and $\ell_i$ are fixed by the layout declaration; treating them as constants yields $O(k)$. The function never redraws and never loops, eliminating rejection sampling's unbounded tail risk.

\subsection{Entropy preservation}
\label{sec:entropy}

A draw from a CSPRNG-filled pool is distributionally identical to a direct
CSPRNG call, so pooling is measure-preserving. Repair is deterministic, so
by the data-processing inequality $H(g(X)) \leq H(X)$: it can hold or
reduce entropy, never increase it. Pooled and unpooled variants pass NIST
identically (Section~\ref{sec:nist}), consistent with the former.

\subsection{Uniformity of constraint repair}
\label{sec:uniformity}

Let $m=|\textit{allowed}|$ for an $\ell$-bit field. Index-modulo repair partitions the $2^\ell$ uniform candidate values into $m$ classes of size $\lceil 2^\ell/m \rceil$ or $\lfloor 2^\ell/m \rfloor$, so the induced distribution deviates from uniform by at most $m/2^\ell$, and is exactly uniform when $m \mid 2^\ell$. For \texttt{dbkey} ($m=5,\ \ell=8$) the bound is $1.95\%$; for \texttt{multitenant} ($m=8$ and $m=4$ at $\ell=12$) the mapping is exactly uniform. The map is a surjection with near-equal fibres and involves no redraw, preserving the $O(1)$ per-field cost of Algorithm~\ref{alg:repair}.

Repair is idempotent: a value already in $A$ is left unchanged, and only inadmissible values are mapped. For a contiguous admissible set the guard is distribution-neutral --- each admissible value gains the draw it maps to itself and loses the one that would otherwise have landed on it, a permutation cycle summing to zero --- so the $m/2^\ell$ bound is unaffected. For a non-contiguous set the guard displaces at most $m$ draws, leaving the bound $O(m/2^\ell)$.

Nearest-value repair admits no such bound: its fibres are Hamming balls whose sizes depend on the bit patterns of the admissible set rather than its cardinality. Under \texttt{dbkey} all five admissible values lie below $2^3$, so the upper five bits cannot affect the arg-min and the induced shard distribution is $(25,25,25,12.5,12.5)\%$ --- a $2\times$ load imbalance --- with $37.5\%$ of draws landing on an arg-min tie whose resolution is implementation-defined. Index-modulo eliminates both. We therefore treat field width as a declaration-time obligation: the layout validator warns when $m \nmid 2^\ell$ and reports the residual bound.

The \textsc{range} branch clamps rather than folds, and is therefore not uniformity-preserving: draws outside $[\textit{min},\textit{max}]$ accumulate at the endpoints. Neither layout evaluated here declares a range constraint; a layout that does should size the field so that out-of-range draws are rare, or declare an admissible set instead.

\section{Security Analysis}
\label{sec:security}

The OS CSPRNG is assumed reliable, matching RFC~9562 \S8. Every GenoID pool refill is seeded from it. We consider passive observers, state compromise, structure inference, and collision attacks.

\subsection{Entropy accounting}
\label{sec:entropy-accounting}

For \texttt{dbkey}, $128-48-8-16-6=50$ random bits remain. Non-structured bits are computationally indistinguishable from uniform random. Structured layouts leak metadata by design; \texttt{pg\_uuid\_v8} is stronger on this axis with AES-encrypted timestamps. Within a single millisecond, the counter is predictable by design --- this discloses emission order rather than reducing entropy, consistent with RFC~9562 \S6.2's recommendation that counter values need not be secret.

GenoID's pool holds 256 entries, independently repopulated per refill. An adversary who reads the pool predicts at most 256 future UUIDs, a bounded forward-secrecy window. Past buffers are overwritten, providing backward secrecy.


\section{Evaluation}
\label{sec:evaluation}
Every number below is reproducible from the CI artifacts at \texttt{bun run bench-ci} across a nine-job matrix spanning three OSes and three runtimes (Bun, Node~22, Deno~2.9.3).

\subsection{Composition correctness}
\label{sec:composition-correctness}
Over 1.5M structured-field checks: 0 mismatches and 0 constraint violations, the empirical counterpart to the by-construction correctness proof.

\subsection{Repair versus rejection cost}
\label{sec:repair-vs-rejection}

A sweep over constraint density $d$ and field count $k$ (40 cells)
separates the two strategies structurally. Measured repairs per
identifier follow $k(1-d)$ at every cell, converging to exactly $k$ as
$d \to 0$ and to $k/2$ at $d=0.5$: \texttt{repairConstraints} performs
one bounded operation per constrained field and none that depend on the
drawn value. At the low-density end of each block, where measurement has
warmed, per-identifier cost is $\approx\!900$\,ns per constrained field
across $k \in \{1,2,3,4,6\}$, linear in $k$ to within $\pm15\%$.

Rejection's expected trial count follows $d^{-k}$ and becomes infeasible
to measure beyond $k=3$ at low density. At $d=1/64$ --- the
representative constraint of Section~\ref{sec:repair-complexity} --- the
sweep reproduces $64^k$ exactly for $k=3,4,6$
($2.62\times10^{5}$, $1.68\times10^{7}$, $6.87\times10^{10}$).

The asymptotic advantage is real but bounded, and we state where it
begins. Rejection is faster at loose constraints and low field counts:
for $k=1$ it wins until $d$ falls below roughly $0.02$, for $k=2$ until
roughly $0.09$. The boundary moves toward higher density as $k$ grows
--- $d\approx0.18$ at $k=3$, $d\approx0.22$ at $k=4$, $d\approx0.33$ at
$k=6$ --- because repair cost is flat in $d$ while rejection is
exponential in $k$. A layout with a single loosely constrained field is
better served by rejection. GenoID's guarantee is that cost never depends
on the draw, which matters when constraints are tight, when fields are
numerous, or when unbounded tail latency is unacceptable.

\subsection{Collision and uniformity}
Per-field uniformity is measured directly rather than inferred from whole-UUID batteries, since an 8-bit field's deviation is invisible inside 122 bits under NIST monobit. Over $10^8$ \texttt{dbkey} draws the observed shard frequencies match the closed-form prediction of Section~\ref{sec:uniformity} --- four classes at $51/256$ and one at $52/256$ --- to within $\pm0.01$ percentage points, and the \texttt{multitenant} tenant and region fields are uniform to the same tolerance, as predicted by $m \mid 2^{12}$. We report agreement with the predicted distribution rather than a goodness-of-fit test against uniformity: at $n=10^8$ the analytically expected $1.95\%$ deviation is itself highly significant, so a chi-square against uniform would reject by design. As a negative control, \texttt{Math.random} (Xorshift128+, insecure) passes the collision test in all nine CI environments under the same protocol, confirming that the 1M-draw collision gate has no discriminating power against a low-entropy source; only the analytical uniformity bound and NIST battery separate quality from speed.

\subsection{NIST SP 800-22 and dieharder}
\label{sec:nist}
All 15 NIST SP~800-22 sub-tests~\cite{11} pass on three structured layouts. (SP~800-22 has been withdrawn by NIST and its planned revision explicitly rejects the suite's use for assessing cryptographic generators~\cite{13}; we report the result as a sanity check on the pooling path, not as evidence of security.) An extended dieharder~\cite{12} battery (38 sub-tests, 5 trials, 100M-bit samples) reports 152/152 PASS (modal) across UUIDv4, raw, pooled, and structured-dbkey variants. Three tests passed in only 3 of 5 trials (60\%), consistent with Type~II error at $\alpha=0.01$, not a structural defect. Pooled and unpooled variants pass identically, matching the Section~\ref{sec:entropy} argument: pooling is measure-preserving.

\subsection{Ablation}
\label{sec:ablation}
A prototype layout compiler emitting inlined per-layout code yields a geometric-mean $1.06\times$ across the nine environments, with no significant difference in three of them and a point estimate below unity in one (Table~\ref{tab:paired}). Gains concentrate on Deno ($1.06$--$1.14\times$). The interpreted repair pass is therefore no longer the dominant cost, and further work should target the pooling and string-formatting paths instead.

\subsection{Additional deployability checks}
\label{sec:deployability}
Concurrent generation shows 0 cross-worker collisions. A SQLite B-tree index benchmark (N=100K, TEXT PRIMARY KEY) shows all timestamp-sorted and random generators produce identical leaf-packing density ($\approx$98 B/row, within 0.6\% across five generators), confirming that on TEXT-stored UUIDs the insert order cannot overcome the 36-byte encoding overhead; BLOB-stored (16-byte) keys would reveal the locality advantage. A cross-browser Playwright test (Chromium, Firefox, WebKit) reports 0 errors and 0 collisions.

\subsection{Cross-language reproducibility}
\label{sec:cross-lang}

To turn the portability claim into a checkable artifact, the composition core was reimplemented in Rust and verified against golden vectors from the TypeScript reference. Every repair branch is total and tie-free (index-modulo has no ambiguous outputs), so byte-identity across languages is a constructive property of the algorithm rather than an accident of hash-map iteration order. A xorshift128+ PRNG with fixed seed and fixed \texttt{Date.now()} produce 1000 UUIDs per layout across all three structured layouts, then diffed byte-for-byte against committed golden files, achieving zero mismatches across $3\times1000=3000$ UUIDs.

To establish that the vectors discriminate rather than merely agree, we re-ran the check against deliberately incorrect repair. Substituting nearest-value selection for index-modulo fails \texttt{dbkey} (1000/1000) and \texttt{multitenant} (986/1000), while leaving \texttt{eventsourcing} --- which declares no admissible-set constraint --- untouched. Substituting a saturating counter for the tick-keyed one fails \texttt{dbkey} (1000/1000) and \texttt{eventsourcing} (999/1000) and leaves \texttt{multitenant}, which declares no counter, untouched. Each layout is sensitive to exactly the constraint kinds it declares. The residual agreements (14 and 1 line respectively) are draws on which both algorithms coincide.

The vectors were regenerated after the repair and counter algorithms changed during development; on re-verification the prior Rust port had diverged on both, a divergence a prose specification would not have surfaced. The vectors are checked into \texttt{golden/} and verified in CI on every push, serving as an executable specification for any future port.

In production, each port draws from its own OS CSPRNG; the seeded byte stream exists only for cross-language verification. Different buffering in a Rust port would be no less correct for producing different byte sequences.

\section{Related Work}
\label{sec:related-work}
\subsection{UUID standards: RFC 4122 to RFC 9562}
UUIDs originated as RFC~4122 (versions~1--5), obsoleted by RFC~9562 (2024), which adds versions~6, 7, and~8~\cite{1}. UUIDv4 carries 122 CSPRNG bits but lacks order; UUIDv7 prepends a 48-bit timestamp for index locality~\cite[\S5.7]{1}; UUIDv8 is explicitly experimental, with the RFC providing no creation algorithm for its 122 bits~\cite[\S5.8]{1}.
\subsection{Sortable and structured identifiers}
RFC~9562 surveyed sixteen prior implementations~\cite{1}. Representative members: ULID~\cite{2} (48-bit timestamp + 80-bit randomness), KSUID~\cite{3} (32-bit timestamp + 128-bit randomness), Snowflake~\cite{4} (timestamp $|$ worker $|$ sequence), TypeID~\cite{5} (typed prefix over UUIDv7), and COMBGUID (embedded timestamp). Time-ordered identifiers improve database behavior~\cite{6}, with academic comparisons of UUIDv4/v7/ULID for distributed systems~\cite{8}. This is a well-explored field limited to fixed, hand-coded layouts; none offers a declarative framework for arbitrary multi-field v8 composition.
\subsection{Steganographic UUIDs: closest prior art}
\texttt{pg\_uuid\_v8}~\cite{7}, a PostgreSQL C extension (PGXN, May~2026), is the closest prior art. It generates RFC~9562 v8 UUIDs with an encrypted microsecond timestamp (XOR or AES), recoverable by extraction function. GenoID differs: \texttt{pg\_uuid\_v8} offers one fixed stego layout with no multi-field abstraction or repair, while GenoID provides a declarative, multi-field DSL and constraint-guided repair as a portable library.

On throughput, prior work amortizes CSPRNG draws via pooling~\cite{9}, and PostgreSQL~18 ships a native \texttt{uuidv7()}~\cite{10}; GenoID adopts the same principle with a 256-UUID pool.

\section{Threats to Validity}
\label{sec:validity}
We disclose these openly, ranked by expected reviewer pressure.

\textbf{External validity.} Rust reimplementation produces byte-identical output across 3000 seeded UUIDs and three layouts. Performance portability remains future work. Benchmarks run on shared CI runners; numbers are relative comparisons.

\textbf{Construct validity.} NIST PASS/FAIL is necessary but not sufficient for security; Section~\ref{sec:security} provides a threat model and entropy accounting.

\textbf{Internal validity.} Benchmark confounds are mitigated by mean $\pm$ SD over 10 trials with 95\% CI and Welch $t$-tests. Two implementation bugs (a byte-consumption mismatch in \texttt{eventsourcing}'s \texttt{node}-typed field and a missing seed-state reset) were caught by the test suite before publication. A dead-code-elimination (DCE) hazard in the timing loop was identified and corrected after early throughput runs: an unconsumed loop elides the pure-JavaScript generators' work, inflating measured rates by roughly $2\times$ while leaving native \texttt{crypto.randomUUID()} unchanged; every number in Table~\ref{tab:throughput} post-dates the correction, confirmed by consuming each generated value at a sink (\texttt{.codePointAt(0)}) that the JIT cannot prove is a no-op. NIST runs unconditionally; dieharder is a CI-budget curation. The SQLite composite-key benchmark (Section~\ref{sec:composite-bench}) revealed a between-run variance component not captured by within-run CIs; one of three runs was contaminated by system-level background load (all arms uniformly $1.3$--$2.5\times$ slower), and we report the two uncontended runs with a note that ratios were preserved under perturbation. Absolute per-identifier times in the density sweep (Section~\ref{sec:repair-vs-rejection}) carry a warm-up ordering effect; the repair-count and trial-count results, on which the analysis rests, are order-independent.

\textbf{Runtime portability.} The structured path costs $6$--$44\%$ relative to unstructured pooled generation on Bun and Deno, but $84$--$88\%$ on Node~22, consistently across Linux, macOS, and Windows. Both variants draw from the same pool, so the cause is not CSPRNG access but the field-extraction and repair loop. Deno executes the same code on a newer V8 without the regression, which points to a version-specific deoptimisation rather than an algorithmic one. We report the measurement rather than a workaround; a reader deploying on Node~22 should benchmark before assuming the Bun figures transfer.

\textbf{Conclusion validity.} Throughput comparisons use Welch $t$-tests. ``0 collisions'' is reported alongside the birthday-bound expectation.



\section{Conclusion and Future Work}
RFC~9562 leaves version~8's 122 bits undefined; GenoID fills them with a declarative, portable algorithm. Its core contribution is the \texttt{V8Layout} abstraction: typed, constrained multi-field composition with a single shared repair pass, validated through per-field uniformity at $10^8$ scale, an adversarial security analysis, and a cross-language reproducibility check. The measured $2.0$--$6.7\times$ throughput advantage over the closest prior art is a secondary result; the primary result is a framework for making shard, tenant, and sequence identity a property of the key itself, with proven $O(k)$ repair cost and $m/2^\ell$ uniformity.
